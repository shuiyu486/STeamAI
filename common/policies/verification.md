# Verification and completion criteria

完成前运行与改动和风险直接匹配的最短验证。判断对象是用户要拿走的成品，而不是实现者刚改的那份源码或一次成功的工具调用。

## 从参照物到交付

- 有旧版、示范、样例或正确输出时，先分清**要保留的外部行为**和用户要改的地方。取一个能区分对错的起点与可观察结果，放进已有任务的「交付」或「完成/退出条件」。用户的新要求优先；旧实现、一次示范、坐标或等待秒数不自动成为需求。先用已有材料，只有歧义会改变成品才问。获得材料不等于获准执行旧程序、录屏或记录键鼠。
- 在相同起点对比参照和候选的可见结果，找**最早能证实的差异**。已有失败记录就用它；若只有「构建成功」或「输入已发」，先走一次已获准的接收者入口。先查能区分剩余解释的那一处，不通读无关实现或报告模板。中间步骤看不到就标未知，不把第一个报错当根因。
- 有依据且在写入范围内，负责人直接改候选，重新生成成品，用刚才失败的用法复验；不是交一段修复建议。能分出过拟合时再换一个输入。保存原输入、参照和失败记录；不要为取证重放已发未明或不可逆的动作。
- 用接收者实际拿到的版本验收：分发工具只带交付文件与声明的依赖，到干净目录走正式入口；资料核对交付稿中的关键判断能否回到获准来源，保留未确认项；界面任务核对目标窗口的实际状态变化。仅在工作区能跑、接口返回成功或成员自报完成，都不能替代这一步。无权限就在原负责人处说明缺哪次验证，不借其它角色绕过。
- 回复用户时指出**拿哪一份、怎样用、实际看到了什么、还有什么不能确定**。一次小验证可以直接回答，不要求每个动作写报告；已有 evidence 给出路径即可。

## 按改动选辅助检查

- 文档或模板：检查引用、预算、格式、source/snapshot 路径和 `git diff --check`。
- 声明式 YAML/JSON：检查语法、引用文件存在性和 snapshot closure。
- 代码或合同：运行 focused tests，再按影响面运行 canonical suite 与静态检查。
- Claude Code 原生行为：区分 synthetic contract、自动 probe 和真实独立 session acceptance；不得相互冒充。
- Verified learning：V1 deterministic、V2 replay、V3 calibrated matched comparison、V4 multiple explicit opt-in field outcomes 分层验证；`accepted`、用户确认、Apply 或 Git staging 不提升等级。
- UI/交互：实际走受影响的用户路径。

完成意味着相关验证通过、没有自己引入的 orphan 文件或旧 runtime fallback。未执行、失败或跳过的验证必须如实说明原因和剩余风险。
