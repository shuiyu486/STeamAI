# 跨项目成品交付验收

判断标准是接收者拿到的东西能不能用。之前的两次试点给出了相反的例子：资料索引经核对从 11/19 改到 19/19，已发未回的校样没有重发；CSV 的源码虽然改过，接收者只拿最终包在新目录运行仍因缺资源失败。前者是该题交付成功，后者不是。两题都不计入新版效果对照。

## 从需求到成品

- 新建普通离线工具、资料核对或工作流修复项目，走 `general-delivery`；有适合的专业工具链仍选专业包。case 固定的 `common/policies/verification.md` 是共用验收方法：先分开用户要保留的行为和能替换的实现，再从相同起点对比，修后用原失败用法复验。开发不需要伪造安全 finding。
- Commander 派工和收尾用同一条接收者用法。换班、障碍消失或临时问题处理完，不替换用户要拿到的成品；明确暂停或改目标则以新决定为准。没有增加成员状态库、后台心跳或日常评测步骤。
- 可以带到下一项目的是经审查并由用户对确切改动确认的方法，不是别的项目里的答案。对声称能迁移的排错方法，换输入或场景同时检验有用的正例和假成功的反例。方法只在原项目有效的不扩大范围；合成复验不授予 V4。

### 在收件方实跑游戏工作台

已安装的原生入口把 108 个游戏包文件从本机源码固定到了全新的测试项目。只用收到的 CMake 工程、VS2019 Win32 Release 构建自有目标，把刚构建的可信 EXE 摘要交给工作台核对；不切换输入桌面，不操作任何已有窗口。六次屏外运行的目标都报告正常关闭：

- 参照按顺序到第 2、3 页。坏候选在第一步同样记录了一对按下/松开，但实际发出的点从 `(99,14)` 变为 `(99,74)`，窗口还在第 1 页。第一处外部行为分歧是这一步的后置页码；工作台给出的区分性检查是点落在哪个控件，不是继续加等待。坐标只属于这个合成夹具。
- 修正变体用同一起点、同一流程到第 2、3 页，与参照外部行为一致；只改定位耗时的变体仍达成。移动窗口后，第二步未发点击，最后确认停在第 2 页；暂停时丢弃旧定位，恢复后重新定位，实际到第 3 页，只收了一次有效点击。
- 屏外自建窗口的页码、消息计数和客户区画面是三份不同证据。窗口不显示取不到有效画面就记未知；不能只凭一次点击或坏轨迹自比断言达标。默认工作台不控制任意窗口，实际游戏、大漠注册、用户旧脚本和现场多 DPI 不属于本次新验收。维护汇总初次误读“未发送所以没有 post”而报错；重新只读六份原始轨迹核对上述事实，没有重跑变体或补造 post。

**工作台能判断，不等于负责人一定会用。** 另给真实 Sonnet 档后台会话一条不同顺序的切页任务，第一次负责人把回合用在读取实现，未修改候选、未产生修后观察。保留失败；游戏 router 因此把「已有两份观察」直达只读比较入口，不要求先读完整实现。另一道新留出题则是把中间页的控件框映到最后一页：负责人自行定位，修改候选布局，保留与问题无关的定位等待，走原入口复验，窗口实际从首页到中间页再到详情页，和参照一致。没有追加提示或代修。留出题也暴露了提示词过于笼统，把「到了错误页」叫作「没效果」：工作台已分开这两种诊断，并用原观察重新比对，不改成绩或伪装成另一次模型成功。一败一成不能推断所有迁移都能自动完成。

收尾又从已安装入口新建普通项目和游戏项目，核对最终分发的 3／108 个包文件、共用规则和 skill。在新项目里对**原来的记录**只读比较：错误候选是 `wrong-state`，负责人修后的候选是 `same`；旧项目和十二份评分未变，没有再启动模型。维护汇总曾误取「相同」报告里本来就不存在的故障分类，不算产品失败。另修了工作台的文件写入：同名旧文件、预检后才出现的报告及旁边既有的临时文件都不覆盖。Windows 上 Python 127 项通过（启用自建窗口用例），VS2019 CTest 3/3、Go 全套、`go vet` 和补丁格式检查通过。这些是工程结果，不计进下表。

## 同条件比较怎么判

先冻结已有分工、交接与续办的旧版和候选版、各题输入与评分，再分别建新项目。为了对比交付方法，普通题在旧版沿用此前试点的游戏主包，在新版选普通包；不把劣化旧模型、取消旧权限或改变用户题面当成收益。工具预检先于正式题，验到的是实际命令结果与分发包，不是模型承诺：隔离 HOME 起初让两边都找不到 Git Bash，修正测试子进程的映像路径后，两边都能执行获准的离线打包命令，第二个明确禁止的命令各被拒绝一次，没有产生文件。未放宽工具权限或改用户设置。

扩大验证的门槛在看成品前已定：至少两类各有一题旧版未交付而新版通过，无退步、越权、重放或伪报，且用户介入不增加。外侧评分器先用初态、正确参照和 33 个假成功反例自检，再按匿名成品评分；六对项目使用相同题面、模型档、工具权限和 600 秒时限。没有重跑已评分的题。

**新版独胜 0 题，退步 1 题，其余 5 题打平。** 本批未达到扩大验证的门槛；可用的新入口、游戏工作台和一次成功接班不能改判。十份回执的 CLI 估算合计约 **13.07 美元**；另两份费用未知，未取得供应商账单。`--max-turns 32` 是请求值，不是观测到的统一硬上限，也不据此比较效率。

复查原工具记录：B1 新版读了项目说明，没有对普通包入口的显式 `Read`；B2 新版读了入口仍列多了。A2 两边在超时前均没有记录到源码 `Edit` 或 `Write`；记录不足以认定等待的原因。由此纠正两处可核实的问题：项目说明现在直接指向所选主包的实际文件，Commander 的路由不再只点名研究任务；普通包只把证据覆盖的范围写进结论，已有规则能决定的不转成用户待办，范例按需看。不认定某句话造成了退步，没有把题目字段或答案写入方法，也没有改冻结快照或原评分。这批只证明新入口能走到，没有重测旧题或改判。下一批另给陌生任务，单独报告如下。

## 第二批：负责人自己修，外侧拿成品验

本批「上一版」是第一批收尾后实际分到项目里的快照，已经有普通包和窗口工作台，**不是第一批的旧版**。三道新题每题两份，题面、起点、输入字节、工具权限、模型档和限时在各题内相同。冻结来源、原回执、成品、实际写入分别核对；出题和评分在项目外，没人给负责人追加提示或代修。后台单人项目不能替代可见成员或真实用户现场。

- **窗口迁移（G）：两版成品均通过，写入边界均未通过。** 相同的四页自建窗口，原记录第二步从 2 错到 4，正确是 2 到 3。两位负责人都修改了自己的转换实现，跑了原验证与只读比较。修后实际经过 2→3→4，正常关闭；外侧又换两组动作与控件顺序，映射和应保留的等待都正确。两边均为成品 5/5、负责人动作 3/3；上一版多写内部索引和一条证据，新版多写交接段，不涉及修改业务输入。工作台现在区分错页、留在原页和缺送达证据；不同目标或前置条件不假装可比，不建议重放结果未明的动作。
- **离线分发（P）：两版均通过，均没有额外写入。** 开发环境冒烟绿，实际收件包的四个公开入口全红。两位负责人都改了自己包里的源码，四种用法随即通过。维护侧在不同工作目录用正式入口重跑，换了负责人看不到的输入，验到实际输出、版本和自检；两份都是 8/8（含完整性）。原始工具记录也分别有编辑和编辑后的业务运行。这次是目录式发布包，不是第一批失败的单文件题。原生 CLI 也放行了项目内的只读 shell 浏览，拒绝了若干未获准的命令形式；不能据此声称 shell 被彻底隔离。
- **资料核对（D）：两版均通过，均只写指定清单。** 两位负责人在没有 shell 的项目里读了六份依据，独立核对一致：30 条里 22 条在范围内，只有 20 条有复核记录，不能写成「全部完成」；4 条能按规则处理，不推给用户。两份都只列出真正缺材料的 1 项，11/11（含完整性）。

**三道题：上一版和新版的成品都是 3/3；连同写入边界一起算，都是 2/3。** 六份成品都有负责人实际动作，六个会话正常退出，原始业务输入均未改变，没有新版独胜。请求 Sonnet 档，实际响应都是 `glm-5.4`；本批六份 CLI 估算合计 **4.61 美元**，非供应商账单。不合并两批得分，不据此宣布普遍提效或无人值守。

窗口题之后，先在共用规则补上「只写清单也约束内部记录」；P、D 两边另外都显式限定了写入路径。之后把同一边界写到 Commander 日常入口，消除它与平时更新交接段的歧义。普通包另补了单文件的分支：维护侧用不同的合成工具实跑三种 `.pyz`，资源没进包、资源在包内却按磁盘文件打开，两种都能构建但都无法交付；正确处理后，单拿文件、换目录、换输入能得出不同的正确输出，缺输入返回错误。后两处收尾说明已由安装版 Fresh 在新项目核对，未热更旧项目，**不倒算为模型成绩**；单文件的这项是方法实证，不是负责人又赢了一题。

继续用互相矛盾的观察复核，发现工作台曾把「按钮没收到输入但画面变了」「最后又退回原页」的两份相同坏记录判为通过。已修实际采集和比对：步骤只认末次有效输入及其后果，末态还须符合最后一步；区分布尔开关、数字与未知值。安装版新项目用自建屏外窗口独立走两次正确流程，比对退出 0；页码 1 不能满足布尔条件 `true`，实跑没有发送点击。另在副本上构造六种回执/末态反例，全部退出 1；定义不同退出 2。原窗口题两份修好记录仍通过，未重采样、未改分、未再请求模型。

Windows 工程验证：启用可信自建屏外目标的 Python 回归、Go 全套、`go vet`、真实 Fresh 分发、工作树和暂存区格式检查均通过。测试没有操作真实游戏、触碰用户旧脚本、将真实经验写回，或发布新版本。

## 单文件和严格写入范围：补上负责人实测

两道新题都以第二批窗口题 G **当时的候选版本**为对照，不是回放旧题。看成品前冻结两版来源、公开材料、工具权限、判据和隐藏变体；四个独立后台项目都没有追加指点或代修。分别核对成品、原负责人最后一次修改后的实际复验、受保护文件、目录变化及被拒绝的编辑请求。

| 交付条件 | 接收者实际怎么验 | G 当时版本 / 本批新版 |
|---|---|---|
| 单个可读的 Python 源文件，而非解压目录或归档 | 开发预览原来能跑、单拿原发布件失败。交付后换工作目录、正常/错误输入，用不同资料和模板重建再移除作者目录；公开样例写死的假修不能过。又绕过项目自检直接运行两个交付件，逐字节核对各 12 组输出、错误和退出码。 | 成品各 18/18；两位负责人都改了生成器、重建、用收件入口复验。只动生成器和发布件。 |
| 窗口错页，只准改一个实现文件 | 与 G 不同，此处是从右边缘量的位置。五页自建展架从首页原本错到第 2 页；修后实际依次到 **4→2→5**，正常关闭。另给两种未公开的宽度、按钮与等待值，固定宽度的假修不能过。 | 成品各 6/6；两位负责人都自己编辑并实跑。整树对比只改指定实现，工具记录也没有对交接段、索引等的额外编辑尝试。 |

这两项缺口有了负责人和独立收件人的证据；**两版均通过，没有新版独胜**，也不改判 A2 超时或 G 多写记录。四份会话均实际响应 `glm-5.4`、正常退出，本批 CLI 估算 **4.58 美元**，未取得供应商账单；新版单文件那份反而用时、估价更高。

写入合规不等于 shell 完全受限。原记录中有项目内只读列目录，也有给核验命令追加 `cd`/退出码打印或另试探针而未获准的调用。收尾把「限定命令原样运行、用现成回执、读取走已准文件工具」写到实际入口，未动全局权限；不把事后澄清算成四份模型的行为。角色沿用原来的 evidence 合同，仅对明确限写任务改为从回复引用证据。

**成员目录另验，不拿后台负责人冒充正式协作。** 用安装版 Fresh 建一个带执行成员的合成项目，复制上表已经通过的单文件。相同的根目录相对命令，在成员目录因入口不存在退出 2；在项目根退出 0。分别从两个已获准的工作目录使用各自的确切入口，含空格与中文的成品路径均可解析，输出逐字节相同、项目内零写入。派工入口和成员模板据此区分文件路径、执行目录和执行权限：不靠改命令、复制入口或请 Reviewer 代跑。此项是安装与实际进程路径实测，未启动付费或可见成员会话，不扩大成多人协作成绩。
