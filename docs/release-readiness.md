# Release readiness checklist

## 读取指南

本文件是发布前的一页门禁说明。新会话和上下文压缩后先读 `docs/context-routing.md`；当前真实使用路线实施时，再读 `docs/real-usage-hardening-roadmap.md` 顶部和当前批次卡。维护者只有在准备 release、合并大型批次或判断 runtime owner 时才读本文件顶部；产品北极星、短 goal、历史迁移和 PowerShell removal 分别按路由读取对应专文。

本文件不替代 `rekit/tests/README.md` 的 smoke 选择指南，也不是要求每次改动都运行全量 PowerShell matrix。当前普通迭代和“现在能不能用”的判断只看 Windows 本机 focused tests、真实产品路径和完整 local gate；不要查询或等待远程 jobs，也不要因为 Linux/macOS、三平台兼容或缺少预编译安装包而降低当前完成度。只有用户明确启动正式发布、跨平台兼容、安装交付专项或周期复审时，才进入这些检查。届时仍要区分 `release-check` inventory ready、本地 gate 通过和远程 jobs green，不能互相冒充。

## 执行清单

### CI release gate

`.github/workflows/release-gate.yml` 当前定义默认轻量 CI 门禁：

- `Go release checks (Linux)` 在 `ubuntu-latest` 上运行 `release-check -Format json`、`status`、`packs`、`doctor`、`go vet ./...` 与 `go test -count=1 -p=2 -timeout=30m ./...`；vet位于tests前，确保测试失败时仍保留静态检查信号。
- `Go release checks (Windows)` 在 `windows-latest` 上运行同一组 Go-native checks，验证 Windows 默认路径不依赖 PowerShell façade。
- `Go release checks (macOS)` 在 `macos-latest` 上运行同一组 Go-native checks，验证 macOS 默认路径。
- CI 不默认运行 `rekit.ps1`、`facade-smoke.ps1`、`pack-smoke-matrix.ps1`、真实临时 case Agent Team smoke 或 heavy-tool gate；这些仍按下面“选择性追加”规则手动选择。

跨平台完成度分三级记录：

1. **repository/runtime portability**：Go packages 与 direct commands 可在对应 runner 构建/测试。
2. **CLI/case E2E**：init/attach/start/reconcile/gate/handoff 等真实临时 case flow 在对应平台通过。
3. **installed user entrypoint readiness**：current 项目的 canonical `/steamai` 与 project-local skill 能定位 verified project-local runtime，不依赖 PATH 或外部 kit；legacy-only `.rekit` 项目的 `/rekit` thin shim 继续作为独立 compatibility 路径验证。

当前 workflow 主要覆盖第 1 级；本地 Go tests 已覆盖 CLI/case E2E product-path slice和legacy installed case shim status/refresh slice。第 3 级 current `/steamai` copied-directory/no-central-kit installed entrypoint E2E已在Windows完成，并作为Batch 828产品完成证据；第 2级和第3级尚未进入Linux/macOS runner matrix。Linux/Darwin/FreeBSD受影响包cross-compile只证明源码可编译，不能作为对应平台runtime或installed-entrypoint证据。

### Windows-first 普通 batch cadence

已授权 commit/push 的普通 batch 默认只有一次 implementation commit/push，覆盖代码、测试、文档与 Windows 本机验证。本机 focused regressions 和完整 release minimum 通过、完成态写回并推送后即可进入下一批；不轮询或等待远程 workflow，不创建专门的 release inspection commit。若完成态文档因同一 implementation commit 无法预写自身 SHA，fresh `release-check` / `status` 会先严格验证最近一次成功`release-run`留下的Git-local v2 validation receipt：当前HEAD必须是receipt baseline后的唯一direct commit，commit路径、status/mode与Git tree blob OID必须等于validated artifact snapshot；receipt同时保留实际验证时工作树SHA-256/bytes，并用`git hash-object --path ... --stdin`记录clean-filter blob OID，避免Windows `core.autocrlf`把合法commit误判为内容漂移。旧schema、缺失或不匹配receipt均fail-closed。随后生成只读 `postPushReceipt`：通常仅当工作树 clean、branch 为 `main`、`HEAD` 与本地已知 `origin/main` tracking ref 相等、captured SHA 的父/当前 batch 恰好是连续且已完成的 transition，并且该 commit 同时包含 batch plan、CHANGELOG 与明确产品 owner 路径时关闭 `implementation-pending`；若已推送implementation commit暴露receipt runtime缺陷，只允许一条由fresh v2 receipt精确验证当前HEAD的同批repair commit完成接力，不能放行其它extra commit。查询绑定同一 captured SHA 并在 ready 前复核 refs/status，dirty、非 main、缺 ref、不同步、移动 snapshot、docs-only、未绑定same-batch repair或歧义 transition 均 fail-closed。该 receipt 不 fetch/pull/push/commit，也不查询或证明 remote CI green。远程 Linux/macOS/Windows jobs 保持异步，只在正式发布、跨平台专项或每 3–5 批周期复审时等待、判断并记录实际结果。
