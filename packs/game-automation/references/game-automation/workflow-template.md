# Game Automation 完整 workflow 模板

一个 Windows 游戏自动化开发任务从分配到交付的主线。步骤是参考框架，硬边界（本文件与 router 中的脚本行为硬边界）才是约束。

## 任务输入（Commander 分配时列出）

- **目标绑定**：窗口标题/类名/进程 identity（exact，不用模糊进程名或全桌面）。
- **目标流程**：期望的状态序列与每个状态的判定条件（可见控件、图像特征或窗口 API 可查的值）。
- **非幂等清单**：流程中提交/支付/领取等只允许发生一次的动作。
- **预算**：动作次数上限、总时长上限、单步等待上限。
- **停止与恢复**：正常停止与紧急停止入口约定、恢复前提。
- **写入范围**：case-relative 项目源码路径（开发交付）。

## 阶段

1. **环境预检**：按 `tooling/integrations/airtest.md` 现场核对版本与窗口绑定（合成窗口上一次低影响真实操作）。
2. **脚本设计**：状态机——枚举所有可观测状态（含失焦、目标消失、意外弹窗、未知），每个状态定义唯一决策；先写决策表再写代码。
3. **fake adapter 单测**：决策核心用 fake adapter 覆盖正常、延迟、错误状态、暂停恢复、停止、重复启动六类（参考 `tooling/catalog.yml` `state-decision-logic`），不启动真实框架。
4. **真实窗口冒烟**：Airtest 绑定目标 → 识别一个状态 → 执行一个安全输入 → 校验结果 → 释放。
5. **场景验收**：按 `tooling/recipes/automation-regression.md` 六场景矩阵实测，记录每个场景的输入时间线与停止时延。
6. **交付**：脚本、配置、依赖锁、使用说明、运行日志与测试观察（evidence）；代码走 code review，绑定源码版本或 exact diff。

## 决策核心结构（与执行框架解耦）

```text
observe() → 状态 + 置信度
decide(state, ledger, config) → 动作 | 等待(上限) | 暂停(原因) | 停止(原因)
act(action) → 记录时间戳；非幂等动作两阶段：先查 ledger → begin(pending 落盘)
              → 执行 → commit(done)；中断后 pending 残留=无法确认，暂停待确认
wait_for(expected, timeout, poll_interval) → 状态轮询，不用固定 sleep 堆叠
```

动作发出后至少隔一个观察轮询再决策下一动作：快输入通道下目标状态更新滞后，
不节流会在旧观察上重发输入。

ledger 持久化已执行的非幂等动作；重新启动或恢复时先 observe 再查 ledger，不从旧计数器继续。

## 停止语义（验收判据）

- 收到停止（正常或紧急）到**不再发新输入** ≤2 秒；无法满足时记录实测上界并修复根因，不把"按键已发送"当停止完成。
- 暂停不等于停止：暂停期间不发新输入，但保持观察；恢复必须从重新 observe 开始。
- 主循环阻塞在外部长调用时，停止须经独立检查点（控制轮询或可中断调用）生效，不能依赖"未来才回来的主循环"。

## 交付边界

- 只交付可修改的脚本/配置/依赖锁/说明，不新增常驻服务或后台守护。
- 示例与配置只用合成窗口和占位符；真实目标身份与凭据不进 pack 或仓库。
- 开发 accepted 不升级 learning 资格；经验回流仍走用户 exact confirmation。
