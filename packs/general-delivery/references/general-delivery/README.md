# General Delivery 按需路由入口

`general-delivery` 用于没有更合适专业方法的普通项目：离线可运行的小工具、资料核对、既有工作流修复。交付的是用户或接收者拿来就能用的成品，加上能让人复现和复查的说明。这是开发或核对任务，不是安全研究：不为它伪造安全 finding，也不套用游戏、逆向、Web 安全包的做法。

## 怎么读

先读 case 的 `.steamai-vnext/CLAUDE.md`，再从下表只选当前任务这一行。表内路径都相对本包根目录：`references/…` 是本包文件；`../../common/…` 上溯两级，指向随 case 一起分发的 `common/`。写进成员任务时，本包文件写 `../../pack-snapshot/packs/general-delivery/<路径>`，common 文件写 `../../pack-snapshot/common/<路径>`。分工、证据、审查和经验回流沿用 case 规则与 common policy。

| 当前任务 | 读取 |
|---|---|
| 新写或修改离线可运行的工具 | 本文「工具」 |
| 核对资料、清单或说法有没有依据 | 本文「资料」 |
| 既有脚本或流程的结果不对 | 本文「修复」 |
| 成品能不能交付、没通过怎么办 | `../../common/policies/verification.md`，成品检验的唯一来源 |
| 受阻于外部工具、要报告可用性 | `../../common/policies/tool-adapters.md` |
| 要操作普通 Windows 软件的界面 | `../../common/tooling/windows-desktop-mcp.md` |
| 需要游戏自动化、逆向、Web 安全等专业方法 | 本文「转出」 |

## 开工前

先定下两件事：

- **接收者怎么用**：谁用、在什么样的环境用、怎么启动、给什么输入、看到什么算成功。能从用户的话和已有材料推出来的直接用。
- **材料各说明什么**：旧版、示范、样例、期望输出分别对应哪一部分要保持的行为。保持的是用户依赖的外部行为，新写法不必照抄旧实现。旧版与用户明确要求的结果冲突时，以用户要求为准；修复阻碍本次交付的原因，保留依据。无关的已知问题单列，不擅自改变用户依赖的行为。原件不改不动，要试就在副本上试。

## 工具

先确认分发物、正式入口、必需的资源和声明过的依赖。用接收者的环境检验，具体做法读 `../../common/policies/verification.md`；不把开发目录也拷过去充当交付。路径带空格、输入编码、运行时等，只检查与本次用法相关的差异。

开发目录冒烟通过、脱离源码却失败时，直接看 `references/general-delivery/examples.md` 的「脱离源码红了：先分四类，再动实现」：先区分入口、丢资源、路径、包版本或业务差异。单文件交付就运行单文件；列得出包内资源不表示能按磁盘路径打开。改自己那处实现，用同样的命令复验，不必先读完整实现。

## 资料

- 关键判断标明出处和适用范围。证据必须覆盖结论指的对象；局部记录不能替代全体的统计或版本结论。
- 区分已证实、已否定和未知。资料没写的不补造。
- 交稿前把稿子逐行过一遍，只看标了「结论」和「待确认」的行：
  - 结论（否定也是结论）：写出证据管到的范围，即哪些条目、哪段时间、哪个版本。结论的范围比它大，就把结论缩到这个范围，或改标未知。
  - 待确认：先在已有规则和默认处理里找。找得到就不是待办，改成“按〈规则〉已处理”写进稿子；只有没有规则能决定、答案又会改变成品的问题才保留。不因名称相似或联想到另一种需求就列为待用户确认。
- 来源冲突时并列出处和适用条件，让接收者能按位置复查。需要例子时，见 `references/general-delivery/examples.md` 范例 B 的「交稿前逐行过」。

## 修复

从能区分对错的最小输入开始，沿数据经过的步骤找差异。查明原因后修必要范围，不因第一处报错就认定是哪一行或哪一个文件坏了。

需要示例时，再看 `references/general-delivery/examples.md`：A 是工具分发，B 是资料核对，C 是流程修复。不必为了交付而走完范例里的每一步。

## 转出

本包不提供下面这些方法，也不替它们验收。

- 操作普通 Windows 软件的界面（截图、点击、输入）：读 `../../common/tooling/windows-desktop-mcp.md`，启用和操作边界以它为准。
- 游戏自动化、二进制或逆向、Web/API 安全等有专门 pack 的对象：case 已把那个包选为辅助 pack 时，读该包 `manifest.yml` 的 `entrypoints.router` 和一个专项入口（成员路径 `../../pack-snapshot/packs/<aux-pack>/…`）。没有选时，向 Commander 说明需要哪个包的哪类方法，由用户决定是否选用；不补装，也不用本包的做法冒充专业验收。

## 要先确认的动作

运行用户提供的旧版程序、录屏或键鼠记录，安装或升级依赖、运行时和打包工具，把成品或资料发出项目目录：都先说明具体动作并取得确认，再动手。
