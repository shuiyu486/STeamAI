# 成品交付范例

三个合成的小例子，用来对照手上的任务。文件、数据和对话都是编的，只演示 `README.md` 和 `../../common/policies/verification.md` 的规则怎么落地，不新增规则。文中 `../../common/…` 相对本包根目录，在成员任务里写成 `../../pack-snapshot/common/…`。

## 范例 A：给旧工具加一列（工具）

**用户给的**

- 旧版程序，示范用法 `merge a.csv b.csv`，结果写到 `out.csv`。运行它已在 case 授权内。
- 样例输入和期望输出：

| 文件 | 内容 |
|---|---|
| `a.csv` | 表头 `id,qty`，数据 `1,2`、`2,3` |
| `b.csv` | 表头 `id,qty`，数据 `2,5`、`3,1` |
| `expected.csv` | 表头 `id,qty`，数据 `1,2`、`2,8`、`3,1` |

- 需求一句话：“输出里加一列来源文件名。”
- 接收者是一位同事，电脑上没有开发环境。

**接收者怎么用**

| 要定的 | 本例 | 从哪来 |
|---|---|---|
| 谁用 | 同事 | 用户说的 |
| 什么环境 | 没有开发环境的 Windows | 用户说的 |
| 怎么启动 | 解压后运行 `merge a.csv b.csv` | 旧版的示范用法 |
| 什么算成功 | `out.csv` 多一列来源，其余行和数值与改动前一样 | 需求加期望输出 |

起点定为一组固定输入，能观察的结果是 `out.csv` 的内容。

**先记下要保持的行为**

用样例实际运行旧版，输出与 `expected.csv` 相同，看得出两条行为：按 `id` 合并，同一 `id` 的 `qty` 相加。还有一点样例看不出来：行是按 `id` 升序，还是按首次出现的顺序？在这组样例上两种结果一样。换一份能分开它们的输入 `c.csv`（数据 `2,1`、`0,5`）与 `a.csv` 合并，旧版实际输出：

```text
id,qty
0,5
1,2
2,4
```

`0` 排在最前，旧版是按 `id` 升序。这三条行为要保持，要改的只有多出一列；新写法不必沿用旧版的代码结构。

**新需求有两种读法**

同一个 `id` 出现在两个文件时（样例里的 `id=2`），来源列写 `a,b`，还是只写先出现的 `a`？样例和期望输出都看不出区别，而它会改变输出。这一个问题要问用户，用户答复“全部列出，按文件名排序”。答复之前它保持未确认，不按自己的猜测交付。

**改动与复测**

- 只增加来源列，合并、相加、排序不动。
- 样例再跑一遍：输出比 `expected.csv` 多一列来源，其余逐行相同。
- `c.csv` 那组再跑一遍，先手算预期 `0,5,c`、`1,2,a`、`2,4,a,c`，实际运行与手算一致。

**脱离源码检验**

1. 打出分发物 `dist.zip`，里面只有程序、运行要用的文件和声明过的依赖。
2. 复制到源码目录之外的一个干净目录解压。另找一个工作目录放样例输入，从那里调用包里的程序：先跑样例，再跑 `c.csv` 那组。
3. 实际看到：两次输出都与上面一致，这一项通过。
4. 没验证的：另一台没装运行库的电脑上能不能启动。写进交付说明，不写成已验证。

**脱离源码红了：先分四类，再动实现**

开发目录冒烟通过，只证明那一份程序在开发条件下能跑。以下拿目录式 Python 分发举例：用同一份包、同一组输入，把实际不同的那一步找出来，不先通读实现。命令各自独立；尖括号换成实际的绝对路径。

```text
python -m zipfile -l "<dist.zip>"
python "<解压目录>/<入口>" "<a.csv绝对路径>" "<b.csv绝对路径>"
```

若两种用法均获准，分别在解压目录外（接收者的方式）和解压目录内，用同一组绝对路径运行第二条。若只准其中一处，就只验那一处；不为了做对照自行换目录或改命令。

| 先看到什么 | 类别 | 要改的一处 |
|---|---|---|
| 启动器找不到入口文件；或列包内容里入口多套了一层目录 | 入口 | 打包的目录层级，或交付说明里的启动命令，二者对齐 |
| 报错指向包里本该有、列包内容里却没有的文件 | 丢资源 | 自己的打包清单，把该文件随包分发 |
| 包外启动失败、包内启动正常 | 路径 | 自己实现里找资源的基准：本目录式分发以程序所在目录为基准，不以当前目录为基准 |
| 两次都跑完、退出 0，内容与期望不同 | 包旧，或业务差异 | 先用下面的比对分清，再决定改哪里 |

报错没写明路径时，在自己的实现里打开文件之前临时打印那个路径，定位后去掉。

跑完但内容不对，可以先比包里的资源和这次构建理应带上的那一份。不同就查打包输入；相同只排除了这一个文件，不代表包内代码、运行环境或业务逻辑都对。拿相同输入比较源码入口与实际分发入口，再按「范例 C」找第一次分歧。

```text
python -c "import filecmp,sys; print(filecmp.cmp(sys.argv[1], sys.argv[2], shallow=False))" "<源码里的资源>" "<解压目录里的同一资源>"
```

**单文件不是解压目录。** 先确认收件人要的是一份可读的脚本，还是可执行归档；换个扩展名不等于交付形式相同。若是生成的脚本，只把脚本交给接收者，让生成时的源码和资料不再可用，再从另一个工作目录按原命令运行。若生成器还要支持资料换版，用新的资料重建再验，别只给同一件成品换输入。比如 Python `.pyz`：把收件人拿到的那一份直接当程序启动，不拿解压后的源码代跑。构建通过、压缩包里也能列出资源，却仍报找不到文件时，先区分两件事：资源是否进包，运行时代码能否按它的存放方式读取。归档内的 `__file__` 不是普通磁盘目录；如果是包内只读数据，可用 `importlib.resources.files(包名)` 下的资源读取接口。用户传入的输入文件仍按原命令读取，不改成相对安装位置。不要用源码目录、旁放的资源或临时改工作目录掩盖问题。

改完重新打包，把新成品单独交到空目录，用刚才失败的命令和输入复验，再换一个能算出不同结果的输入。若原用法约定缺输入会报错，也核对实际错误与退出码。保留能复查的原失败和修后结果，不动原件。

**交付说明**

拿哪一份（`dist.zip`）、启动命令、运行环境要求、输入输出放哪里、来源列的规则、没验证的部分。

**做不下去时**

打包工具本机没有、安装没获准：“从分发物启动”这次验证就做不了。如实告诉 Commander 缺的是哪一次验证、获准后要做的最小动作；工具可用性按 `../../common/policies/tool-adapters.md` 报告。

## 范例 B：核对一份功能清单（资料）

**用户给的**

三份资料 `<手册-v1>`、`<发布说明-v2>`、`<常见问题>`，和一份要核对的功能清单。核对结果要随清单一起发给看的人；看的人不用再来问哪条有依据，才算成功。

**逐条核对**

| 清单上的说法 | 找到的来源 | 结论 |
|---|---|---|
| 支持导入 Excel | `<手册-v1>`「导入」一节：“仅支持 CSV”；`<发布说明-v2>`「新增」一节：“新增 Excel 导入” | 已证实，仅 v2 起 |
| 单次导入的上限是 10 万行 | 三份资料都没有这个数字；`<常见问题>` 只写“数据量大时建议分批” | 未知，资料没写 |
| 导出的文件是 UTF-8 编码 | `<手册-v1>`「导出」一节第三段：“UTF-8”；`<常见问题>`“乱码”一条：“导出为 ANSI” | 两份说法冲突，见下 |

第二条最容易出错：不能写成“最多 10 万行（据常见问题）”，因为常见问题里没有这个数字。想提醒用户注意风险，另起一行标「推断」。

**交稿前逐行过**

只看稿子里标了「结论」和「待确认」的行，各问一句：结论的范围有没有超出证据管到的范围；待确认的事有没有已有规则能决定。

| 稿子原来写的 | 问题 | 改成 |
|---|---|---|
| 结论：导出会丢行（据 `<常见问题>`） | 依据只有 3 条用户反馈，只证明有这 3 次报告；肯定和否定“会丢行”都超出范围 | 结论：收到 3 条“导出丢行”的反馈；是否真丢、占比多少未知，资料没写 |
| 待确认：要不要保留 `<默认排序>` | `<迁移规则>` 已写明默认保留，规则能决定，不是待办 | 按 `<迁移规则>` 保留默认排序，不列入待确认 |

留下来的待确认，只能是没有任何规则能决定、而且答案会改变成品的问题。

**说法冲突时**

UTF-8 和 ANSI 可能对应不同版本，也可能其中一份过时。能拿到程序时各导出一个文件看实际编码；拿不到就并列两条出处、保持未知，由用户决定以哪份为准。

**换一份资料再核**

用户后来给了 `<手册-v2>`，其中明确写着“单次导入上限为 5 万行”。原清单的“上限是 10 万行”对 v2 应从未知改为已否定，正确值是 5 万行；v1 的上限仍然未知。

**别人怎么复查**

复查的人只拿交付稿和这几份资料：按每条的来源位置打开，翻得到依据，这条就站得住；有一条翻不到，退回原负责人。每条都带着结论和适用条件，复查的人不需要来问作者。

## 范例 C：流程结果不对（修复）

- 现象：`<流程>` 是“读取 → 整理 → 导出”三步。用户说导出表里「备注」一列全空，上周还有内容。
- 复现：用上周同一份输入跑一遍，仍然全空。
- 两种解释：整理这一步就没把「备注」带过来；或者带了，导出这一步丢了。
- 区分：看整理步骤的中间文件，「备注」有内容。前一种排除，问题在导出这一步。
- 改动：只改导出对「备注」列的处理。用原来那份输入再跑，「备注」恢复；再跑用户平时用的另外两份输入，各列与上周结果一致。
